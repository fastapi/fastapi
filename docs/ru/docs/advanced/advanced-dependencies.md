# Продвинутые зависимости { #advanced-dependencies }

## Параметризованные зависимости { #parameterized-dependencies }

Все зависимости, которые мы видели, — это конкретная функция или класс.

Но бывают случаи, когда нужно задавать параметры зависимости, не объявляя много разных функций или классов.

Представим, что нам нужна зависимость, которая проверяет, содержит ли query-параметр `q` некоторое фиксированное содержимое.

Но при этом мы хотим иметь возможность параметризовать это фиксированное содержимое.

## «Вызываемый» экземпляр { #a-callable-instance }

Не сам класс (он уже является вызываемым), а экземпляр этого класса.

## Ограничение одновременного использования зависимости { #limit-dependency-concurrency }

В некоторых случаях может потребоваться ограничить количество HTTP-запросов, которые могут одновременно использовать зависимость.

Например, у вашей базы данных может быть ограниченное количество доступных подключений. Вы можете заставить новые HTTP-запросы ждать перед созданием сессии, пока другой HTTP-запрос не закончит использовать свою сессию.

Для этого можно использовать `max_concurrency` в `Depends()`.

Обновим псевдоним `SessionDep` из [руководства по базам данных SQL](../tutorial/sql-databases.md):

```Python
SessionDep = Annotated[Session, Depends(get_session, max_concurrency=5)]
```

Теперь до **пяти HTTP-запросов** могут одновременно держать открытыми сессии базы данных через эту зависимость.

Если другому HTTP-запросу нужна сессия, он ждёт, пока одна из этих сессий не закроется.

Во время ожидания он **не занимает рабочий поток**, поэтому эти потоки доступны для выполнения другого кода.

Значение должно быть положительным целым числом. По умолчанию используется `None`: это означает, что FastAPI не ограничивает количество одновременных выполнений зависимости.

### Общий лимит для нескольких маршрутов { #share-the-limit-between-routes }

Все маршруты в этом примере используют один и тот же псевдоним `SessionDep`, поэтому у них общий лимит в пять сессий.

Чтобы лимит был общим, повторно используйте **один и тот же объект `Depends()`**, например в псевдониме `Annotated`, как в этом примере.

Если для каждого маршрута создать новый `Depends(get_session, max_concurrency=5)`, у каждого будет собственный лимит в пять сессий. Это верно даже в том случае, если все они используют одну и ту же функцию `get_session`.

Повторное использование того же `SessionDep` в другом приложении также делает лимит общим, если оба приложения работают в одном цикле событий. Это относится и к смонтированным приложениям.

Например, если два приложения используют этот `SessionDep` для одного и того же пула подключений к базе данных, вместе они могут держать открытыми до пяти сессий через эту зависимость.

Если приложения используют отдельные пулы и им нужны независимые лимиты, создайте отдельный объект `Depends()` для каждого приложения.

### Закрытие сессии перед разрешением открыть следующую { #close-the-session-before-allowing-another-one }

В этом примере `get_session` использует `yield`. Сессия учитывается в лимите, пока код завершения не закончит её закрытие.

Параметр `scope` зависимости определяет, когда выполняется этот код завершения:

* При `scope="request"` (значение по умолчанию) он выполняется после отправки HTTP-ответа.
* При `scope="function"` он выполняется после завершения *функции-обработчика пути*, до отправки HTTP-ответа.

Подробнее можно прочитать в разделе [Раннее завершение и scope](../tutorial/dependencies/dependencies-with-yield.md#early-exit-and-scope).

Для зависимости без `yield` вызов учитывается в лимите только до завершения функции.

Если вы используете зависимость с `yield` в обработчике WebSocket, она учитывается в лимите до выхода из обработчика и окончания выполнения кода завершения зависимости.

/// note | Примечание

Повторное использование [кешированного значения зависимости](../tutorial/dependencies/sub-dependencies.md#using-the-same-dependency-multiple-times) не учитывается в лимите повторно. Если разные объявления используют одно и то же значение, вызов учитывается только в лимите того объявления, которое вызывает зависимость.

///

### Выбор лимита для вашего приложения { #choose-a-limit-for-your-application }

Выберите лимит, соответствующий количеству подключений к базе данных, доступных этим сессиям.

Если другие части вашего приложения тоже используют эти подключения, оставьте запас и для них. FastAPI не знает размер вашего пула подключений к базе данных.

У каждого воркер-процесса свой лимит. Например, два воркер-процесса с этой зависимостью могут суммарно держать открытыми до десяти сессий.

/// note | Технические детали

Лимиты также независимы для каждого цикла событий. Приложения, работающие в разных циклах событий, не имеют общего лимита, даже если повторно используют один и тот же объект `Depends()`.

///

### Зависимости, которым нужно несколько ресурсов { #dependencies-that-need-more-than-one-resource }

FastAPI выполняет подзависимости зависимости до применения её лимита.

Поэтому, чтобы ограничить количество сессий базы данных, укажите `max_concurrency` в `Depends(get_session, ...)`, где создаётся сессия.

HTTP-запрос может заблокироваться, если ему нужна ещё одна сессия, а он всё ещё удерживает сессию, которая закроется только в конце HTTP-запроса.

Например, представьте общий объект `Depends(get_session, max_concurrency=1, use_cache=False)`, который используется дважды в одном HTTP-запросе.

Первый вызов создаёт сессию. Второй вызов ждёт её закрытия. Но первая сессия не может закрыться, пока HTTP-запрос не завершится, а HTTP-запрос ждёт второго вызова.

Два HTTP-запроса также могут заблокироваться, если один удерживает сессию, ожидая другой ресурс, а второй удерживает этот ресурс, ожидая сессию.

Если вашим HTTP-запросам нужны несколько ресурсов, получайте их в одном и том же порядке. FastAPI применяет каждый лимит отдельно и не резервирует заранее все ресурсы, которые понадобятся HTTP-запросу.

## Зависимости с `yield`, `HTTPException`, `except` и фоновыми задачами { #dependencies-with-yield-httpexception-except-and-background-tasks }

/// warning | Предупреждение

Скорее всего, вам не понадобятся эти технические детали.

Они полезны главным образом, если у вас было приложение FastAPI версии ниже 0.121.0 и вы столкнулись с проблемами зависимостей с `yield`.

///

Зависимости с `yield` со временем изменялись, чтобы учитывать разные случаи применения и исправлять проблемы. Ниже — краткое резюме изменений.

### Зависимости с `yield` и `scope` { #dependencies-with-yield-and-scope }

В версии 0.121.0 FastAPI добавил поддержку `Depends(scope="function")` для зависимостей с `yield`.

При использовании `Depends(scope="function")` код после `yield` выполняется сразу после завершения *функции-обработчика пути*, до отправки HTTP-ответа клиенту.

А при использовании `Depends(scope="request")` (значение по умолчанию) код после `yield` выполняется после отправки HTTP-ответа.

Подробнее читайте в документации: [Зависимости с `yield` — раннее завершение и `scope`](../tutorial/dependencies/dependencies-with-yield.md#early-exit-and-scope).

### Зависимости с `yield` и `StreamingResponse`, технические детали { #dependencies-with-yield-and-streamingresponse-technical-details }

До FastAPI 0.118.0, если вы использовали зависимость с `yield`, код после `yield` выполнялся после возврата из *функции-обработчика пути*, но прямо перед отправкой HTTP-ответа.

Идея состояла в том, чтобы не удерживать ресурсы дольше необходимого, пока HTTP-ответ «путешествует» по сети.

Это изменение также означало, что если вы возвращали `StreamingResponse`, код после `yield` в зависимости уже успевал выполниться.

Например, если у вас была сессия базы данных в зависимости с `yield`, `StreamingResponse` не смог бы использовать эту сессию во время стриминга данных, потому что сессия уже была закрыта в коде после `yield`.

В версии 0.118.0 это поведение было возвращено к тому, что код после `yield` выполняется после отправки HTTP-ответа.

/// note | Примечание

Как вы увидите ниже, это очень похоже на поведение до версии 0.106.0, но с несколькими улучшениями и исправлениями краевых случаев.

///

#### Сценарии с ранним выполнением кода после `yield` { #use-cases-with-early-exit-code }

### Зависимости с `yield` и `except`, технические детали { #dependencies-with-yield-and-except-technical-details }

До FastAPI 0.110.0, если вы использовали зависимость с `yield`, затем перехватывали исключение с `except` в этой зависимости и не пробрасывали исключение снова, исключение автоматически пробрасывалось дальше к обработчикам исключений или к обработчику внутренней ошибки сервера.

В версии 0.110.0 это было изменено, чтобы исправить неконтролируемое потребление памяти из‑за проброшенных исключений без обработчика (внутренние ошибки сервера) и привести поведение в соответствие с обычным поведением Python-кода.

### Фоновые задачи и зависимости с `yield`, технические детали { #background-tasks-and-dependencies-with-yield-technical-details }

До FastAPI 0.106.0 вызывать исключения после `yield` было невозможно: код после `yield` в зависимостях выполнялся уже *после* отправки HTTP-ответа, поэтому [Обработчики исключений](../tutorial/handling-errors.md#install-custom-exception-handlers) к тому моменту уже отработали.

Так было сделано в основном для того, чтобы можно было использовать те же объекты, «отданные» зависимостями через `yield`, внутри фоновых задач, потому что код после `yield` выполнялся после завершения фоновых задач.

В FastAPI 0.106.0 это изменили, чтобы не удерживать ресурсы, пока HTTP-ответ передаётся по сети.

/// tip | Совет

Кроме того, фоновая задача обычно — это самостоятельный фрагмент логики, который следует обрабатывать отдельно, со своими ресурсами (например, со своим подключением к базе данных).

Так код, скорее всего, будет чище.

///

Если вы полагались на прежнее поведение, теперь ресурсы для фоновых задач следует создавать внутри самой фоновой задачи и использовать внутри неё только данные, которые не зависят от ресурсов зависимостей с `yield`.

Например, вместо использования той же сессии базы данных, создайте новую сессию в фоновой задаче и получите объекты из базы данных с помощью этой новой сессии. И затем, вместо передачи объекта из базы данных параметром в функцию фоновой задачи, передавайте идентификатор этого объекта и заново получайте объект внутри функции фоновой задачи.
